# Linux Infrastructure Lab — развёртывание Linux-инфраструктуры, контейнеризация приложений и локальная AI-среда

## 1. Общая информация о проекте

Linux Infrastructure Lab — практический проект по развёртыванию, настройке и сопровождению Linux-инфраструктуры с использованием виртуализации, контейнеризации приложений и локальных инструментов искусственного интеллекта.

В рамках проекта была подготовлена виртуальная среда на базе Oracle VM VirtualBox с установленной Ubuntu Linux 22.04 LTS (64-bit). Внутри Linux-окружения выполнялось развёртывание сервисов, настройка программной среды, запуск контейнеризированных приложений, проверка доступности сервисов и изучение инструментов системного администрирования.

Отдельное направление проекта — организация локальной AI-среды на базе Ollama и языковой модели DeepSeek. Модель запускается на локальном оборудовании, что позволяет взаимодействовать с ней через командную строку и использовать её без постоянного обращения к облачным AI-сервисам.

Для развёртывания веб-сервисов используется Docker. В рамках работы был запущен Nginx в отдельном контейнере, а также развёрнут сайт WordPress с помощью Docker Compose. Контейнеризация позволила организовать запуск приложений в изолированных окружениях, управлять их жизненным циклом и контролировать состояние сервисов стандартными средствами Docker.

Проект охватывает несколько взаимосвязанных направлений:

- администрирование Linux-систем;
- виртуализация и подготовка серверного окружения;
- контейнеризация приложений с использованием Docker;
- управление многокомпонентными приложениями через Docker Compose;
- развёртывание и проверка веб-сервисов;
- работа с локальными языковыми моделями;
- взаимодействие с HTTP API;
- анализ состояния процессов, служб и контейнеров;
- диагностика проблем запуска и доступности приложений;
- организация хранения данных и подготовка инфраструктуры к мониторингу.

Основной акцент сделан на практической работе с сервисами: от первоначального развёртывания до проверки работоспособности, изучения конфигурации, анализа состояния и управления запущенными компонентами.

## 2. Виртуализация и подготовка Linux-окружения

### Oracle VM VirtualBox и Ubuntu Linux

В качестве среды виртуализации используется Oracle VM VirtualBox. Виртуальная машина предназначена для развёртывания и тестирования Linux-сервисов в изолированной среде без необходимости устанавливать серверное программное обеспечение непосредственно в основную операционную систему компьютера.

Внутри виртуальной машины установлена Ubuntu Linux 22.04 LTS с архитектурой x86-64. Данная среда используется как основа для запуска контейнеризированных приложений, локального AI-сервиса и выполнения административных операций.

В процессе работы с виртуальной машиной используются базовые инструменты Linux для изучения структуры файловой системы, получения информации об операционной системе, проверки ресурсов и управления программным окружением.

Примеры команд для работы с системой:

```bash
# Информация об установленной операционной системе
cat /etc/os-release

# Информация о ядре Linux
uname -a

# Проверка архитектуры системы
uname -m

# Информация о процессоре
lscpu

# Информация об оперативной памяти
free -h

# Проверка свободного пространства на дисках
df -h

# Просмотр текущего каталога
pwd

# Просмотр файлов и каталогов
ls -lah
```

Эти инструменты позволяют получать сведения об окружении, оценивать доступные ресурсы и выполнять первичную проверку системы перед запуском приложений.

Для организации рабочего пространства используются стандартные средства командной строки Linux: создание каталогов, просмотр файлов, редактирование конфигураций и выполнение команд с необходимыми правами доступа.

Примеры:

```bash
# Создание каталога для инфраструктурных компонентов
mkdir -p ~/infrastructure-lab

# Переход в рабочий каталог
cd ~/infrastructure-lab

# Создание отдельных каталогов для конфигураций
mkdir -p docker/nginx
mkdir -p docker/wordpress
mkdir -p docs

# Просмотр структуры каталогов
find ~/infrastructure-lab -maxdepth 3 -type d
```

В ходе работы также используются механизмы управления пакетами Ubuntu, включая `apt`, для установки и обновления программного обеспечения и необходимых зависимостей.

```bash
# Обновление списка доступных пакетов
sudo apt update

# Поиск пакета в репозиториях
apt search <название-пакета>

# Проверка установленной версии пакета
apt policy <название-пакета>

# Просмотр установленных пакетов
dpkg -l
```

### Управление службами и процессами

Для управления системными службами используется systemd. Основным инструментом взаимодействия с ним является `systemctl`, позволяющий проверять состояние служб, запускать и останавливать их, выполнять перезапуск и настраивать автоматический запуск при загрузке операционной системы.

Примеры команд:

```bash
# Проверка состояния Docker Engine
systemctl status docker --no-pager

# Проверка состояния Ollama
systemctl status ollama --no-pager

# Проверка служб, завершившихся с ошибкой
systemctl --failed

# Просмотр состояния автоматического запуска службы
systemctl is-enabled docker

# Просмотр списка активных служб
systemctl list-units --type=service --state=running
```

Для диагностики используются системные журналы. Инструмент `journalctl` позволяет анализировать сообщения служб и определять причины ошибок запуска или нестабильной работы.

```bash
# Последние 100 записей журнала Docker
sudo journalctl -u docker -n 100 --no-pager

# Просмотр журнала в режиме реального времени
sudo journalctl -u docker -f

# Журнал Ollama за последний час
sudo journalctl -u ollama --since "1 hour ago" --no-pager
```

Дополнительно используются инструменты просмотра процессов и потребления ресурсов:

```bash
# Список процессов
ps aux

# Интерактивный мониторинг процессов
top

# Средняя нагрузка системы
uptime

# Список процессов с сортировкой по использованию памяти
ps aux --sort=-%mem | head
```

Работа с этими инструментами формирует понимание жизненного цикла системных служб, различий между процессом приложения и службой управления, а также основных подходов к первичной диагностике Linux-систем.

## 3. Контейнеризация приложений с использованием Docker

### Установка и организация контейнерной среды

Docker используется для запуска приложений в изолированных контейнерах. Контейнеризация позволяет отделять окружение приложения от основной операционной системы, использовать готовые образы, управлять параметрами запуска и воспроизводить конфигурации.

В рамках проекта Docker применяется для развёртывания веб-сервера Nginx и многокомпонентного приложения WordPress.

Работа с Docker включает управление контейнерами и образами, проверку состояния запущенных приложений, просмотр журналов, анализ параметров контейнеров и контроль сетевого взаимодействия.

Основные команды:

```bash
# Проверка версии Docker
docker --version

# Проверка информации о Docker Engine
docker info

# Просмотр запущенных контейнеров
docker ps

# Просмотр всех контейнеров, включая остановленные
docker ps -a

# Просмотр локальных образов
docker images

# Просмотр сетей Docker
docker network ls

# Просмотр Docker volumes
docker volume ls

# Мониторинг потребления ресурсов контейнерами
docker stats
```

Особое внимание уделяется различию между образом и контейнером. Образ содержит файловую систему и необходимые компоненты приложения, а контейнер представляет собой запущенный экземпляр приложения с определёнными параметрами, сетевыми настройками и состоянием.

Для получения подробной информации о контейнерах используется `docker inspect`. Команда позволяет анализировать параметры запуска, настройки сети, подключённые тома, переменные окружения и другие характеристики контейнера.

```bash
# Подробная информация о контейнере
docker inspect <container_name>

# Просмотр опубликованных портов
docker port <container_name>

# Просмотр последних записей журнала
docker logs --tail 100 <container_name>

# Просмотр журнала в реальном времени
docker logs -f <container_name>
```

При диагностике проблем используются последовательная проверка состояния контейнера, анализ журналов приложения и проверка параметров его запуска. Это позволяет отделять проблемы самого приложения от проблем контейнерной конфигурации, сетевой доступности и системных ресурсов.

## 4. Развёртывание веб-сервера Nginx в Docker

### Организация запуска веб-сервера

В рамках проекта был развёрнут Nginx в Docker-контейнере.

Nginx используется как веб-сервер для обработки HTTP-запросов. В зависимости от конфигурации он может обслуживать статические файлы, работать в качестве reverse proxy и обеспечивать входную точку для веб-приложений.

Запуск Nginx в контейнере позволяет изучить практическую организацию веб-сервера в изолированном окружении, управление сетевыми портами и контроль состояния приложения с помощью инструментов Docker.

В процессе развёртывания рассматриваются следующие аспекты:

- использование готового Docker-образа Nginx;
- создание и запуск контейнера;
- настройка публикации портов;
- проверка состояния контейнера;
- проверка HTTP-доступности веб-сервера;
- просмотр журналов приложения;
- управление остановкой и повторным запуском контейнера;
- диагностика ошибок запуска и сетевой доступности.

Типовой пример запуска контейнера Nginx:

```bash
docker run -d \
  --name nginx-lab \
  --restart unless-stopped \
  -p 8080:80 \
  nginx:stable
```

В данном примере контейнер запускается в фоновом режиме, получает имя `nginx-lab`, использует политику автоматического перезапуска и публикует порт 80 контейнера на порту 8080 хостовой системы.

Параметры примера показывают один из вариантов развёртывания. Для воспроизведения первоначальной конфигурации необходимо использовать фактические значения, применённые при запуске сервиса.

После развёртывания выполняется проверка состояния контейнера и доступности веб-сервера.

```bash
# Проверка состояния контейнера
docker ps -a

# Проверка опубликованных портов
docker port nginx-lab

# Просмотр журнала Nginx
docker logs --tail 100 nginx-lab

# Проверка HTTP-ответа
curl -I http://127.0.0.1:8080

# Подробная диагностика HTTP-соединения
curl -v http://127.0.0.1:8080
```

Команда `curl` используется для проверки фактического ответа сервера. Это позволяет отличать ситуацию, когда контейнер просто запущен, от ситуации, когда веб-сервис действительно принимает и обрабатывает HTTP-запросы.

При возникновении проблем проверяются состояние контейнера, публикация порта, доступность соответствующего TCP-порта и сообщения в журнале приложения.

Управление жизненным циклом контейнера выполняется стандартными средствами Docker:

```bash
# Остановка контейнера
docker stop nginx-lab

# Повторный запуск
docker start nginx-lab

# Перезапуск контейнера
docker restart nginx-lab

# Проверка состояния после перезапуска
docker ps -a
```

Такой подход позволяет контролировать состояние веб-сервера и выполнять базовые операции сопровождения контейнеризированного приложения.

## 5. Развёртывание WordPress с использованием Docker Compose

### Организация многокомпонентного приложения

В рамках проекта был развёрнут сайт WordPress с использованием Docker Compose.

WordPress представляет собой веб-приложение, для полноценной работы которого требуется база данных. Контейнерная архитектура позволяет запускать приложение и его зависимости как отдельные сервисы, объединённые общей сетью и конфигурацией.

Docker Compose используется для описания состава приложения в YAML-файле и управления его компонентами в рамках единого проекта.

В отличие от ручного запуска каждого контейнера, Compose позволяет централизованно задавать образы, параметры запуска, переменные окружения, сетевую конфигурацию и постоянное хранение данных.

При работе с подобной архитектурой рассматриваются следующие компоненты:

- сервис веб-приложения WordPress;
- сервис базы данных, используемый конкретной конфигурацией;
- параметры подключения приложения к базе данных;
- внутренняя сеть между контейнерами;
- публикация HTTP-порта;
- постоянное хранение файлов и данных;
- управление запуском и остановкой сервисов;
- анализ журналов отдельных компонентов.

### Работа с Docker Compose

Основные команды управления:

```bash
# Проверка версии Docker Compose
docker compose version

# Проверка и отображение итоговой конфигурации
docker compose config

# Запуск сервисов в фоновом режиме
docker compose up -d

# Просмотр состояния сервисов
docker compose ps

# Просмотр всех журналов проекта
docker compose logs

# Просмотр последних записей журнала
docker compose logs --tail 100

# Непрерывный просмотр журналов
docker compose logs -f

# Просмотр журнала отдельного сервиса
docker compose logs wordpress

# Перезапуск сервисов
docker compose restart

# Остановка сервисов
docker compose stop

# Остановка и удаление контейнеров проекта
docker compose down
```

Команды выполняются в каталоге проекта, содержащем файл `compose.yaml` или `docker-compose.yml`.

Перед запуском конфигурации можно использовать `docker compose config`, чтобы проверить корректность YAML-структуры и получить итоговое представление параметров приложения.

### Проверка состояния приложения

После запуска WordPress выполняется проверка состояния контейнеров и доступности веб-приложения.

```bash
# Просмотр контейнеров
docker ps -a

# Состояние сервисов Compose
docker compose ps

# Анализ журналов WordPress
docker compose logs --tail 100 wordpress

# Просмотр опубликованных портов
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

# Проверка HTTP-доступности
curl -I http://127.0.0.1:<опубликованный-порт>
```

Проверка журналов позволяет выявлять ошибки запуска, проблемы подключения к базе данных, ошибки конфигурации и другие неисправности, возникающие при работе приложения.

При диагностике недоступности WordPress необходимо последовательно проверять состояние контейнеров, правильность публикации порта, готовность базы данных и параметры подключения приложения к ней.

### Сетевое взаимодействие между сервисами

В Docker Compose контейнеры одного проекта могут взаимодействовать друг с другом через внутреннюю сеть Docker.

В типовой конфигурации приложение WordPress подключается к базе данных по имени сервиса, а не через `localhost`. Это связано с тем, что внутри контейнера `localhost` указывает на сам контейнер.

Понимание этого принципа важно при настройке взаимодействия между компонентами приложения и диагностике ошибок подключения.

Для анализа сетевой конфигурации используются:

```bash
# Список сетей Docker
docker network ls

# Подробная информация о сети
docker network inspect <network_name>

# Информация о контейнере и его сетевых параметрах
docker inspect <container_name>
```

### Постоянное хранение данных

При эксплуатации контейнеризированных приложений необходимо учитывать различие между файловой системой контейнера и постоянным хранилищем.

Для данных, которые должны сохраняться после пересоздания контейнеров, используются Docker volumes или bind mounts.

В контексте WordPress это особенно важно для сохранения файлов приложения, пользовательских загрузок и содержимого базы данных.

Для проверки конфигурации хранения используются:

```bash
# Список Docker volumes
docker volume ls

# Информация о конкретном томе
docker volume inspect <volume_name>

# Информация о подключённых томах контейнера
docker inspect <container_name>
```

Правильная организация постоянного хранения позволяет отделить жизненный цикл контейнера от жизненного цикла данных и снижает риск их случайной потери при обновлении или пересоздании сервисов.

## 6. Локальная AI-инфраструктура: Ollama и DeepSeek

### Развёртывание языковой модели

В рамках проекта развёрнута локальная языковая модель DeepSeek с использованием Ollama.

Ollama используется как среда запуска языковой модели и предоставляет интерфейс для управления моделями и взаимодействия с ними через локальный API.

Основная особенность данного решения заключается в возможности обрабатывать текстовые запросы непосредственно на локальном оборудовании. После загрузки необходимых файлов модели и подготовки окружения для выполнения генерации не требуется постоянно обращаться к внешнему облачному AI-сервису.

Локальная AI-среда используется для проверки работоспособности языковой модели, взаимодействия с ней через командную строку и изучения возможностей дальнейшей интеграции с другими приложениями.

### Проверка установленного окружения

Для проверки состояния Ollama используются следующие команды:

```bash
# Проверка версии
ollama --version

# Список локально доступных моделей
ollama list

# Проверка состояния службы
systemctl status ollama --no-pager

# Просмотр журнала службы
sudo journalctl -u ollama -n 100 --no-pager

# Проверка локального API
curl http://127.0.0.1:11434/api/tags
```

Команда `ollama list` позволяет определить, какие модели доступны для запуска в текущем окружении.

HTTP-запрос к `/api/tags` используется для проверки доступности локального API и получения списка загруженных моделей.

### Взаимодействие с моделью

Запуск модели выполняется через CLI Ollama:

```bash
ollama run <имя-модели>
```

После запуска пользователь может отправлять текстовые запросы и получать ответы непосредственно в терминале.

Для автоматизированного взаимодействия Ollama предоставляет HTTP API, что позволяет обращаться к модели из внешних приложений и интеграционных сценариев.

Пример запроса к API генерации:

```bash
curl http://127.0.0.1:11434/api/generate \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<имя-модели>",
    "prompt": "Объясни, как диагностировать остановленный Docker-контейнер",
    "stream": false
  }'
```

В запросе задаётся модель, текст задания и режим получения ответа. При отключённой потоковой выдаче API возвращает результат генерации одним ответом.

Использование HTTP API создаёт основу для дальнейшей интеграции модели с приложениями, автоматизированными сценариями и Telegram-ботом.

### Работа без постоянного подключения к интернету

В рамках проекта проверяется возможность использования локальной модели без постоянного обращения к внешним AI-сервисам.

После предварительной загрузки модели и необходимых файлов Ollama может выполнять генерацию локально. При этом загрузка новых моделей, обновление программного обеспечения и получение отдельных зависимостей могут требовать подключения к интернету.

Для подтверждения автономной работы необходимо проверять фактическую доступность модели при отключённом внешнем сетевом соединении.

В таком тесте важно убедиться, что:

- модель присутствует в локальном хранилище;
- служба Ollama доступна;
- запрос к API успешно обрабатывается;
- ответ формируется без обращения к удалённому AI API.

### Контроль системных ресурсов

Работа локальной языковой модели создаёт нагрузку на процессор, оперативную память и дисковую подсистему.

Для наблюдения за ресурсами используются:

# Проверка оперативной памяти
free -h

# Интерактивный мониторинг нагрузки

Эти команды помогают оценивать потребление ресурсов и выявлять возможные ограничения локального окружения при работе с языковой моделью.

## 7. Диагностика и сопровождение сервисов

При работе с инфраструктурой используется последовательный подход к диагностике, основанный на проверке состояния приложения, анализе журналов, проверке сетевой доступности и оценке системных ресурсов.

Для контейнеризированных приложений применяются следующие инструменты:

```bash
docker ps
docker ps -a
docker logs --tail 100 <container_name>
docker inspect <container_name>
docker stats
docker network ls
docker volume ls
```

Для системных служб:

```bash
systemctl status <service_name> --no-pager
systemctl --failed
sudo journalctl -u <service_name> -n 100 --no-pager
sudo journalctl -u <service_name> -f
```

Для проверки ресурсов и сетевых параметров:

```bash
free -h
df -h
uptime
ps aux
ip addr
ip route
ss -lntp
```

Для проверки HTTP-доступности:

```bash
curl -I http://127.0.0.1:<port>
curl -v http://127.0.0.1:<port>
```

При возникновении неисправности диагностика начинается с определения фактического состояния сервиса. Затем проверяются журналы, параметры запуска, сетевые настройки и зависимости приложения.

Например, если контейнер не запускается, сначала выполняется `docker ps -a`, после чего изучаются журналы через `docker logs` и конфигурация через `docker inspect`.

Если контейнер находится в состоянии `Up`, но веб-приложение недоступно, дополнительно проверяются публикация портов, TCP-доступность, HTTP-ответ и журналы веб-сервера.

Такой подход позволяет разделять проблемы операционной системы, контейнерной инфраструктуры, сетевого взаимодействия и самого приложения.

## 8. Безопасность и управление конфигурацией

При работе с инфраструктурными сервисами учитываются базовые принципы безопасного хранения конфигурации и управления доступом.

Ключевые аспекты:

- исключение паролей и токенов из открытых конфигурационных файлов;
- разделение конфигурации приложения и его секретов;
- контроль опубликованных сетевых портов;
- использование отдельных пользователей для работы с базами данных;
- ограничение доступа к сервисам, которым не требуется внешняя доступность;
- проверка версий используемых компонентов;
- понимание различий между временными данными контейнера и постоянным хранилищем;
- подготовка механизмов резервного копирования для приложений с важными данными.

Для конфигурационных файлов Docker Compose предпочтительно использовать переменные окружения и отдельные файлы локальной конфигурации, не содержащиеся в открытой документации.

При публикации примеров конфигураций следует использовать демонстрационные значения и исключать реальные учётные данные.

Отдельное внимание уделяется версии операционной системы и совместимости компонентов. Для стабильной работы инфраструктуры необходимо использовать поддерживаемые версии ОС и программного обеспечения.

## 9. Архитектурное развитие инфраструктуры

Развёрнутая среда рассматривается как основа для дальнейшего расширения инфраструктуры дополнительными сервисами.

Следующие направления развития:

- PostgreSQL для организации реляционного хранилища и работы с тестовыми данными;
- Zabbix для централизованного мониторинга доступности сервисов и системных ресурсов;
- контейнеризация интеграционного приложения для работы с Ollama;
- Telegram-бот для отправки запросов локальной языковой модели и получения ответов;
- автоматизация проверок состояния сервисов;
- стандартизация конфигураций и сценариев развёртывания.

### PostgreSQL

Планируется развернуть PostgreSQL и подготовить тестовую базу данных для практической работы с SQL.

В рамках этого направления предполагается создание таблиц, добавление тестовых записей, выполнение SELECT-запросов, проверка прав доступа и изучение резервного копирования.

### Zabbix

Планируется развёртывание Zabbix для мониторинга Linux-хоста и сервисов инфраструктуры.

В качестве объектов мониторинга предполагаются системные ресурсы, доступность веб-сервисов, состояние контейнеров и доступность локального API Ollama.

### Интеграция локальной языковой модели

Следующим этапом является интеграция Ollama с контейнеризированным приложением.

Предполагается реализовать приложение, которое принимает запрос, обращается к локальному API модели и возвращает полученный результат. При этом потребуется определить сетевую архитектуру, параметры подключения, обработку ошибок и способ запуска интеграционного сервиса.

### Telegram-бот

Планируется разработать Telegram-бота, который будет передавать сообщения пользователя локальной языковой модели и возвращать сгенерированные ответы.

Такой компонент позволит объединить локальную AI-среду, HTTP API и прикладную логику в единую систему.

При этом для взаимодействия с Telegram потребуется сетевой доступ к Telegram Bot API, даже если сама генерация ответов выполняется локально.

Следующее направление развития — расширение инфраструктуры за счёт PostgreSQL, Zabbix и прикладного приложения, интегрирующего локальную языковую модель с Telegram.
